# مَخزَن — أرشيف ZIP و7Z على GitHub

صفحة عربية متجاوبة لحفظ الملفات المضغوطة في GitHub وتنزيلها لاحقًا. تدعم الملفات الصغيرة والكبيرة دون تحميل الملف الكامل في ذاكرة الخادم.

## المزايا

- قبول ZIP و7Z بالسحب والإفلات أو الاختيار من الجهاز.
- التحقق من الامتداد وتوقيع الأرشيف ومطابقتهما.
- تخزين الملفات حتى 100 MiB في مجلد `uploads/` داخل المستودع.
- تقسيم الملفات الأكبر تلقائيًا إلى أجزاء داخل **GitHub Release**.
- تقسيم ملف **7 GiB إلى 4 أجزاء**؛ حجم الجزء الأقصى 1.75 GiB، أي أقل من حد GitHub البالغ 2 GiB لكل Release asset.
- إنشاء Release كمسودة أولًا، ونشره فقط بعد وصول جميع الأجزاء.
- زر إلغاء يحذف المسودة والأجزاء غير المكتملة.
- تنزيل الملف الكبير كملف واحد؛ يدمج الخادم الأجزاء بالترتيب أثناء التدفق.
- عرض الحجم والتاريخ وعدد الأجزاء، مع الحذف وفتح الملف في GitHub.
- إبقاء رمز GitHub في الخادم فقط وعدم إرساله إلى المتصفح.

## التشغيل

يتطلب **Node.js 20 أو أحدث**.

```bash
npm install
cp .env.example .env
```

عدّل `.env`:

```dotenv
GITHUB_OWNER=your-username
GITHUB_REPO=your-private-repository
GITHUB_BRANCH=main
GITHUB_TOKEN=your-fine-grained-token
MAX_FILE_SIZE_GB=20
```

ثم شغّل التطبيق:

```bash
npm start
```

وافتح `http://localhost:3000`.

> يمكن استخدام `GITHUB_REPOSITORY=owner/repository` بدلًا من `GITHUB_OWNER` و`GITHUB_REPO`، ويمكن تمرير الرمز عبر `GH_TOKEN` بدلًا من كتابته في `.env`.

## صلاحية GitHub المطلوبة

يُفضّل إنشاء **مستودع خاص مخصص للأرشيف** واستخدام Fine-grained personal access token:

1. اختر المستودع المستهدف فقط في **Repository access**.
2. ضمن **Repository permissions → Contents** اختر **Read and write**؛ وهذا يشمل إنشاء Releases وإدارتها.
3. ضع الرمز في بيئة الخادم أو `.env` المحلي. ملف `.env` مستبعد من Git.

## كيف يُحفظ ملف 7 جيغا؟

1. يقرأ المتصفح توقيع الملف فقط، ثم يطلب خطة رفع.
2. ينشئ الخادم Release مسودة وبيانات وصفية تحتوي اسم الملف وحجمه وترتيب الأجزاء.
3. يستخدم المتصفح `Blob.slice()` لإرسال جزء بحجم 1.75 GiB في كل مرة؛ لا يقرأ ملف 7 GiB كاملًا في الذاكرة.
4. يمرّر الخادم كل جزء إلى `uploads.github.com` كتدفق ثنائي دون تخزينه على القرص أو تجميعه في الذاكرة.
5. بعد اكتمال الأجزاء الأربعة، يُنشر الإصدار ويظهر كملف واحد في الأرشيف.
6. عند التنزيل، يطلب الخادم الأجزاء بالترتيب ويرسلها للمتصفح كملف `.7z` واحد مع `Content-Length` الأصلي.

## متطلبات الشبكة والنشر

الرفع المجزأ يحتاج إلى وصول الخادم إلى:

- `api.github.com` لإنشاء الإصدار وإدارة بياناته.
- `uploads.github.com` لرفع الأجزاء.
- مضيفي التنزيل الذين يحوّل إليهما GitHub عند قراءة Release assets.

تفحص الصفحة قناة الرفع **قبل** إنشاء المسودة. إذا كانت بيئة المعاينة تحجب `uploads.github.com` فستظهر رسالة واضحة، ولن يبدأ نقل ملف ضخم بلا فائدة. عند النشر خلف Nginx أو reverse proxy، اسمح بجسم طلب يصل إلى 1.75 GiB ومهلات طويلة، ويفضل تعطيل تخزين الطلب المؤقت مثل `proxy_request_buffering off`.

## الحدود والتخزين

- الحد الافتراضي للملف الأصلي هو **20 GiB** ويمكن تغييره عبر `MAX_FILE_SIZE_GB` حتى 100 GiB.
- الملفات حتى 100 MiB تُحفظ بصيغة:
  `uploads/<timestamp>-<unique-id>-<original-name>.<zip|7z>`
- الملفات الأكبر تُحفظ كأجزاء في Release، وليست داخل سجل Git ولا تحتاج Git LFS.
- جلسات الرفع المجزأ موجودة في ذاكرة الخادم؛ إعادة تشغيله أثناء الرفع تتطلب بدء العملية من جديد. تُنظّف المسودات المتروكة تلقائيًا بعد 48 ساعة.
- عند نشر الصفحة للعموم، ضعها خلف تسجيل دخول أو شبكة خاصة حتى لا يستخدم الآخرون صلاحية الرفع الخاصة بك.
