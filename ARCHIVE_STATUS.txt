الوضع الفعلي الآن
-----------------

الإصلاح الحالي
--------------
1. حجم جزء المستودع الآن 16 MiB لتقليل مهلات معالجة البيانات المضغوطة عالية العشوائية.
2. يعيد الخادم المحاولة حتى 3 مرات عند مهلات القواعد وأخطاء 408 و429 و500 و502 و503 و504 والانقطاعات المؤقتة.
3. بعد خطأ بوابة أو شبكة، يفحص الخادم إن كان الجزء محفوظًا فعلًا قبل إعادة إرساله لمنع التكرار.
4. ملف 7 GiB يُقسّم إلى 448 جزءًا، وملف المستخدم الحالي يحتاج 441 جزءًا في قناة المستودع.

التحقق الفعلي
-------------
- نجح رفع جزء اختبار 32 MiB ثم حذفه.
- نجح لاحقًا رفع جزء عشوائي 16 MiB، وتطابق SHA-256 محليًا وعلى GitHub، ثم حُذف بنجاح.
- ملفات upload-probe.7z وrandom-upload-probe.7z اختبارات تقنية وليست ملف المستخدم ولا أرشيفات محفوظة.

ما تفعله الصفحة تلقائيًا
------------------------
1. التقسيم يتم في المتصفح أثناء الرفع باستخدام Blob.slice، دون تحميل الملف كاملًا في الذاكرة.
2. إذا كانت Releases متاحة تُستخدم أجزاء حتى 1.75 GiB؛ وإذا كانت محجوبة تُستخدم uploads/large/ بأجزاء 16 MiB.
3. تُنشأ manifest.json بعد اكتمال الأجزاء، وعند التنزيل تُدمج ليصل ملف 7Z واحد.
4. لكل عملية ملف حالة نصي داخل uploads/status/ يوضح الأجزاء المكتملة والمتبقية.

تعليمات لمن يعمل على المشروع لاحقًا
------------------------------------
- لا تفترض أن ملف 7Z الكبير موجود على GitHub اعتمادًا على الكود أو الاختبارات.
- افحص Releases وuploads/large/ وuploads/status/ قبل إخبار المستخدم بأن الملف محفوظ.
- الجاهز فقط STATUS_CODE: COMPLETE مع manifest مكتمل أو Release منشور مكتمل الأجزاء.
- IN_PROGRESS وINCOMPLETE وCANCELLED وDELETED لا تمثل أرشيفًا أصليًا جاهزًا.
